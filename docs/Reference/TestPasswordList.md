## 三、建议初始化顺序

1. 在空的临时数据目录中通过 Setup 创建 `Admin`，确保其成为首管理员。
2. 创建 `Admin2` 后再由 `Admin` 将其提升为管理员，保留两个活跃管理员以测试最后管理员保护。
3. 创建 `User1`、`User2`、`UnassignedUser`、`ResetUser`、`SessionUser`、`TokenUser` 和 `DeleteUser`，初始均保持普通用户、已激活状态。
4. 通过正常审批流程建立 `PendingUser` 的待审批状态；测试结束后可审批、拒绝或重建，不与其他账号复用邮箱。
5. 先创建并登录 `DisabledUser`，保存仅用于本地验证的测试会话/Token，再由管理员禁用，以验证即时失效和清理行为。
6. 按当前 UI/API 支持的正常路径让 `UnassignedUser` 进入无有效组分配状态；若某项单元测试必须直接建立数据库 fixture，应在测试记录中明确说明，不把 fixture 操作当作生产流程。
7. 涉及删除、重置、角色变化或 Token 轮换的测试前记录账号基线；完成后重建受影响账号，不改变本清单中的统一凭据约定。

## 四、使用规则

- 不要把本文件中的账号导入生产数据库、生产备份或真实邮件系统。
- 动态安全测试必须使用合成订阅、规则、节点、Token 和邮箱内容，不得混入真实凭据。
- OIDC-only 用户没有本地密码，不适合直接套用本清单；OIDC 测试应由本地 mock Provider 独立创建身份与 claims。
- SMTP 测试应使用本地 mock/捕获服务；即使邮箱以 `@test.com` 结尾，也不得尝试向公网发送邮件。
- 每次测试开始时确认实际角色、状态和组分配，不得只凭用户名推断数据库状态。
- 请求/响应、截图和日志证据中如包含 Cookie、Bearer 或下载 Token，仍须脱敏；统一测试密码公开不代表其他测试凭据可以公开。
- 如需增加账号，继续使用唯一用户名、唯一 `@test.com` 邮箱和密码 `12345678`，并在表中说明专属测试用途，避免多个测试破坏同一账号状态。
