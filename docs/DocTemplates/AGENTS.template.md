## 二、核心编码原则

### 简单轻量化

- 功能做减法，不引入不必要的抽象和重型框架
- 优先使用语言标准库，不引入非必要的第三方框架/库
- 单二进制（或最小运行时依赖）分发，无运行时依赖

### 不过度防御

- 聚焦核心场景，不对极端边界做过度防御性编程
- 合理假设输入有效性，不做无意义的 nil/空值检查链
- 错误处理到位即可，不堆叠冗余的 fallback 逻辑

### 安全设计（内部使用导向）

- 项目以**内部使用**为设计前提，<WebUI/管理端>不针对公开访问设计
- 网络安全边界由用户自己控制（防火墙、VPN、反向代理等）
- <管理端>默认绑定本机回环地址，端口冲突时自动回退到可用端口
- 敏感凭据通过独立环境变量传入，不与业务配置混合

### 开箱即用

- 最小化前置依赖，首次运行即可工作
- 配置有合理默认值，无必填项阻塞启动
- 启动后日志提示访问地址/使用方式，用户手动访问即可

### 不确定时主动提问

- 遇到模糊需求、多种可行方案或技术取舍时，使用提问工具询问用户
- 提问时**必须附上推荐选项**并简要说明理由
- 不要在假设下自行决定关键设计

## 三、<外部系统>操作约束

- **绝不**使用全量覆盖类 API（会误删非本工具管理的数据）
- **只用**增量添加 + 精确删除
- 所有由本工具创建的对象，通过对应的标记字段标识，格式：
  ```
  [TAG] comment
  ```
  示例：`[auto-sync] 业务说明`
- 不同后端系统的标记字段可能不同，均以 `[TAG]` 前缀识别
- 删除时"对象已不存在"视为成功（幂等），不报错
- 添加时"对象已存在"视为成功，WARN 日志并跳过
- <其他业务级约束，按需补充：协议支持范围、格式拆分规则、边界处理等>

## 四、<核心子模块>约束（如数据获取/解析约束）

- 使用自定义上游服务（环境变量指定地址）
- 同时处理多类数据（如双栈解析），输出格式有明确约定
- 数据获取失败：记录 WARN 日志，保留现有状态不变（不删除）
- 超时统一为 **<10s>**（可通过环境变量配置）
- 渐进式熔断：连续失败达阈值后熔断，半开状态每轮探测一次，成功后解除
- <其他子模块约束按需补充>

## 五、调度约束

- 使用 `time.Ticker`（或等效标准机制），不依赖外部调度库
- 间隔由 `<INTERVAL>` 环境变量控制（如 `5m`、`30m`、`1h`）
- 优雅退出：收到停止信号后，完成当前轮次再退出
- 支持配置热重载（管理端修改后通过 channel 通知调度器）
- 全局开关（默认开启）：暂停时定时触发与手动触发均不生效；预览/测试类操作不受影响（独立于主循环）

## 六、乐观锁与重试

- 每次写入前重新拉取最新状态（Read → Diff → Create/Delete）
- 不依赖后端版本号参数（由后端自行管理）
- 写入失败自动重试（最多 <3> 次，指数退避）
- 重试时重新走完整流程：Read → Diff → Create/Delete
