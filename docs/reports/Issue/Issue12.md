### R26-01 Clash YAML 头部表单字段缺失、层级扁平且默认值偏离个人配置

- **来源：** 装配页 Clash - V2Ray/Mihomo（新版）头部表单的浏览器评论与用户确认的 UI 调整范围。
- **现象：** 页面仅平铺 `port`、`socks-port`、`mode`、`log-level` 和 `allow-lan`。`redir-port`、`tproxy-port`、完整 Geo 数据、DNS、NTP 及其开关没有结构化入口；当前默认值还写入个人模板之外的 `external-controller`，并把日志级别预填为 `info` 而非个人配置中的 `warning`。长配置需要切换到整个头部 JSON，难以安全维护嵌套数组和对象。
- **根因：** `HeaderStep.vue` 的 Clash 字段 schema 仅覆盖早期最小头部集合，且全局“高级 JSON”模型不能对复杂子配置提供清晰分区；默认值没有与 `Clash.yaml.template.md` 的头部同步。
- **影响范围：** 影响 Clash YAML 装配的编辑效率、默认产物语义和开关可发现性；不影响后端的 `fixed_params`、生成 API、蓝图快照、节点/代理组/规则步骤和既有历史版本。
- **修复方案：**
  1. 头部改为端口配置、Geo 数据、DNS 配置、更多参数四个默认折叠分区；端口/Geo/DNS/更多全部支持结构化编辑和分区级高级 JSON。
  2. 默认头部改为个人模板中的端口、Geo、NTP、DNS 和其他顶层参数；`mixed-port` 保持端口分区可选字段，不默认写入。
  3. 每个分区内的 bool 统一置于本分区“开关参数”区；DNS 的数组改为可增删结构化行，更多参数保留未知顶层键以兼容旧蓝图和扩展字段。
  4. 维持现有 `fixed_params_text`、预览过期和“使用默认值”确认语义，不新增后端接口或数据库迁移；设计结论同步至 Design3 §8.4。
- **验收范围：** 分区默认折叠、模板默认值、分区开关位置、分区 JSON、未知顶层键保留、SR 头部行为回归；前端 Vitest、`npm run build`、`git diff --check`，以及本地页面桌面/移动断点布局核验。
- **状态：** ✅ 暂时完成（2026-09-03：代码与自动化验收已完成；人工桌面/移动页面、结构化/JSON、模板默认值及响应式回归已迁移至 [ProdTestList.md](../../../ProdTestList.md) §五，待人工后续手动处理；不代表人工测试已通过）。

### R26-02 节点检查接口与正式保存未复用同一套完整校验链

- **来源：** Build18.md Step 3/4 验收核验；HEAD 6f98916 的静态代码审查及后端全量测试。
- **现象：** 编辑草稿的检查接口可能返回通过或警告，但提交同一份草稿时正式保存返回 400。当前检查流程在解析当前状态后直接执行 ValidateCurrentState；正式保存还会执行 validateProtocolFields，因此未激活分支中的非法字段可能被检查流程漏过、却在保存时被拒绝。
- **快速验证：** backend/internal/node/check.go:102-113 的编辑检查路径未调用 validateProtocolFields；backend/internal/node/node.go:434-460 的 UpdateManual 同时校验输入协议字段和合并后的协议字段。以当前网络为 tcp 但携带非法 ws-opts 结构为例，检查会跳过未激活分支，保存会在协议字段校验处失败。现有自动化测试和全量 go test ./...、go test -race ./... 均通过，但没有覆盖“检查成功后保存失败”的回归场景。
- **可能根因：** 检查与保存分别维护校验步骤，没有抽取统一的“合并、解析当前状态、凭据/扩展保护、字段校验、目标校验”准备流程。
- **影响范围：** 节点编辑器的检查结果不再能可靠地代表保存结果；前端后续接入目标检查后会出现误导性的成功提示，接口调用方也会遇到检查/保存语义不一致。
- **修复方向：** 抽取保存与检查共用的节点草稿规范化及完整校验函数；检查接口复用该函数后再生成目标诊断。补充非法 inactive 分支、非法字段类型、检查成功后保存成功/失败的一致性测试。
- **待确认事项：** 无产品决策；需按 Design4.md/Build18.md 已确定的统一保存与检查契约修复并补测。
- **状态：** ✅ 暂时完成（2026-09-03：代码与自动化回归已完成；检查/保存一致性、非法 inactive 分支和字段错误的人工 API/UI 回归已迁移至 [ProdTestList.md](../../../ProdTestList.md) §五，待人工后续手动处理；不代表人工测试已通过）。

### R26-03 URI 导入绕过组合校验并保留旧顶层路径别名

- **来源：** Build17/Build18 节点来源适配核验；Design4.md §十六要求手动录入与 URI 导入经过统一规范化。
- **现象：** URI 导入目前只执行协议字段基础校验和当前状态解析，未执行 ValidateCurrentState；因此可导入随后在手动保存中会被拒绝的非法协议组合。同时，VLESS/VMess/Trojan URI 解析会保留旧的顶层 path、host 等别名并写入嵌套传输选项，导入后的协议参数可能同时存在两套表达。
- **快速验证：** backend/internal/node/uri_import.go:88-107 只调用 validateProtocolFields 和 resolveCurrentState，随后直接加密写入原始 Params；backend/internal/node/project.go:321-361 对 SS cipher=auto、Trojan h2/http/xhttp、VLESS XHTTP mode=none 等组合执行更严格的当前状态校验。backend/internal/uriparse/uriparse.go:406-457 可见 VLESS 解析同时处理顶层和嵌套传输字段；backend/internal/assembly/render_clash.go:202-213 会渲染全部协议参数。现有 URI 测试覆盖正常样例，但未覆盖非法组合和旧别名归一化。
- **可能根因：** URI 适配层沿用了早期“解析后直接落库”的路径，没有接入与手动保存相同的规范化、组合校验和冲突字段清理。
- **影响范围：** URI 导入得到的节点可能处于不可用或与表单状态不一致的状态；不同输出目标可能读取不同层级的同名参数，造成配置漂移、兼容性问题和难以定位的导入结果。
- **修复方向：** 将 URI 解析结果转换为统一协议表单模型，清理旧顶层别名并保留规范化后的嵌套路径；导入前复用保存/检查共用的完整校验链，对不满足当前状态的 URI 返回可定位的导入错误，不将原始冲突对象直接落库。
- **待确认事项：** 无产品决策；具体旧字段到规范字段的映射应以 Design4.md 的统一规范化契约补充回归样例。
- **状态：** ✅ 暂时完成（2026-09-03：代码与自动化回归已完成；合法/非法 URI、逐行回执、旧别名归一化和刷新后列表回归已迁移至 [ProdTestList.md](../../../ProdTestList.md) §五，待人工后续手动处理；不代表人工测试已通过）。

### R26-04 Trojan 自定义传输元数据与后端组合校验冲突

- **来源：** Build18.md 首批四协议矩阵核验；Design4.md 对自定义传输和目标能力诊断的约定。
- **现象：** 协议注册表将 Trojan 的 h2、http、xhttp 标记为可手动输入的自定义传输，但当前状态校验又无条件拒绝这三类网络。结果是用户无法保存或检查这些自定义值，系统也无法按设计输出“保留自定义值并针对目标给出不支持/降级诊断”。
- **快速验证：** backend/internal/node/registry.go:467-477 将 Trojan 的 AllowCustom 设为 true，并在帮助文本中列出 h2/http/xhttp；backend/internal/node/project.go:349-353 却直接拒绝这些 network；backend/internal/node/project_test.go:100-125 目前还把 Trojan h2 被拒绝固化为测试预期。Build18.md:146-147 与 Design4.md:246-248、921-922 对“自定义值保留、目标侧诊断、不能当作普通支持组合”的语义不一致。
- **可能根因：** “表单允许录入自定义值”和“核心/目标支持该组合”被合并成了同一个保存前硬拒绝条件，未区分存储合法性与目标可表达性。
- **影响范围：** Trojan 自定义传输无法进入统一保存/检查链；Build18 声称的自定义传输兼容与目标诊断契约无法覆盖该协议，相关测试也会阻止后续按设计修正。
- **修复方向：** 保留 schema 允许的自定义传输值，在协议层仅校验结构与必要字段；由目标检查/装配阶段报告 core_semantic_unexpressible 或相应降级诊断，并更新现有拒绝型测试为保存成功、目标诊断符合预期的测试。
- **待确认事项：** 已确认遵循 Design4.md 的“保存自定义值、目标侧诊断”语义。
- **状态：** ✅ 暂时完成（2026-09-03：代码与自动化回归已完成；Trojan 自定义 h2/http/xhttp 的保存、检查、目标诊断和输出回归已迁移至 [ProdTestList.md](../../../ProdTestList.md) §五，待人工后续手动处理；不代表人工测试已通过）。

### R26-05 VLESS/VMess security 兼容投影可能保留过期 tls 状态

- **来源：** Build18.md 表单层 security 到历史 tls 字段兼容投影核验。
- **现象：** 当旧协议参数中已存在 tls=false，而新表单提交 security=tls 且请求未携带 security reset 时，保存转换只在 tls 字段不存在时写入 tls=true；随后 security 被移除，落库对象可能继续保留 tls=false。检查阶段的当前状态投影会暂时屏蔽该矛盾，但持久化值与用户提交的 security 语义不一致。
- **快速验证：** backend/internal/node/project.go:400-413 的 protocolParamsForStorage 只在 tls 不存在时从 security 写入 tls；同一文件 :27-31 的 ProjectActive 会将 security 映射为 tls=true，从而可能掩盖落库后的旧值。Build18.md:360-362 只记录了预期的 security 兼容投影，现有测试未覆盖“旧 tls 与新 security 同时存在、且未 reset”的场景。
- **可能根因：** 新旧字段合并和兼容投影的优先级不一致；实现依赖前端显式 reset 清除旧字段，后端未对直接 API 调用或缺失 reset 的草稿做最终归一化。
- **影响范围：** 节点重新编辑、导出或后续目标装配可能读取到与检查投影不同的 tls 值，形成状态漂移；也会降低 API 调用方绕过前端时的兼容性。
- **修复方向：** 在服务端最终归一化阶段明确 security 与 tls 的优先级：有新 security 时覆盖/清理旧 tls，并为明确关闭语义写入对应值；补充有旧字段、无旧字段、显式 reset 和直接 API 调用四类回归测试。
- **待确认事项：** 无产品决策；需确认后端不能把清理旧兼容字段的责任完全交给前端。
- **状态：** ✅ 暂时完成（2026-09-03：代码与自动化回归已完成；旧 `tls` 与新 `security` 混合数据的编辑回显、保存后投影和输出回归已迁移至 [ProdTestList.md](../../../ProdTestList.md) §五，待人工后续手动处理；不代表人工测试已通过）。

### R26-06 节点更新静默丢弃顶层未知协议字段

- **来源：** Build18.md 未知字段保护核验；Design4.md §六.4 关于未知扩展字段不可丢失的约定。
- **现象：** 节点更新合并协议 JSON 时只按当前 FieldSchema 构造顶层输出，未登记的顶层字段不会进入结果，也不会返回错误或扩展归属提示。已有嵌套未知字段能够保留，但顶层未知字段没有同等保护。
- **快速验证：** backend/internal/node/node.go:914-939 的 mergeProtocolJSON 只遍历 schema 字段并跳过未知顶层输入；backend/internal/node/project_test.go:69-98 只验证嵌套未知字段保留，没有顶层未知字段回归测试。当前无旧数据会降低立即影响，但 URI 导入、未来协议字段或第三方 API 提交仍可能触发静默丢失。
- **可能根因：** 顶层合并器把 schema 字段集合当成完整输出集合，未实现 extensions 保留或未知字段显式拒绝机制。
- **影响范围：** 用户提交的协议扩展可能在保存后消失，后续编辑/导出无法恢复原值，属于不可逆的数据完整性风险。
- **修复方向：** 在统一保存契约中明确未知顶层字段策略：按协议和目标归属转存到 extensions 并保留，或在无法归属时返回带字段路径的校验错误；在策略落地前禁止静默丢弃，并增加顶层/嵌套未知字段测试。
- **待确认事项：** 已确认未知顶层字段采用“先显式拒绝并要求归入 extensions”。
- **状态：** ✅ 暂时完成（2026-09-03：代码与自动化回归已完成；创建/更新/检查/URI 导入遇到未知顶层字段时的显式拒绝与数据库不变回归已迁移至 [ProdTestList.md](../../../ProdTestList.md) §五，待人工后续手动处理；不代表人工测试已通过）。

### R26-07 禁止编辑 Xray 节点的 PUT 接口错误返回 400

- **来源：** API 错误码核验；AGENTS.md §四.8 规定 403 表示权限不足。
- **现象：** 节点检查接口遇到禁止编辑的 Xray 节点时正确返回 403，但节点更新 PUT 接口把 ErrForbidden 与 ErrBadRequest 一并映射为 400，调用方无法区分请求校验错误和权限/资源状态限制。
- **快速验证：** backend/internal/server/node.go:121-127 的检查处理器单独将 ErrForbidden 映射为 403；同文件 :151-162 的更新处理器却将 ErrForbidden 与 ErrBadRequest 合并映射为 400。现有服务端测试未覆盖禁止编辑节点的 PUT 状态码。
- **可能根因：** 更新处理器沿用旧的 bad request 分支，未同步检查处理器已经采用的权限错误映射。
- **影响范围：** 管理端前端和外部 API 客户端会将权限/资源限制误判为表单错误，影响错误提示、重试策略和接口契约一致性。
- **修复方向：** 将 ErrForbidden 独立映射为 HTTP 403，并补充更新接口的权限错误、校验错误和冲突错误状态码测试。
- **待确认事项：** 无产品决策；按 AGENTS.md 既定错误码契约修正。
- **状态：** ✅ 暂时完成（2026-09-03：代码与自动化回归已完成；禁止编辑 Xray 节点的 PUT 403、校验错误和冲突错误状态码回归已迁移至 [ProdTestList.md](../../../ProdTestList.md) §五，待人工后续手动处理；不代表人工测试已通过）。
