## 一、进行中问题

### R19-01 素材池同步大量 URL 数据时长期占用唯一数据库连接，导致系统整体无响应

- **现象：** 新建素材池并同步少量数据（约 100~200 行）时正常；同步大量数据（如 `https://raw.githubusercontent.com/Loyalsoldier/v2ray-rules-dat/release/direct-list.txt`）时，系统“彻底失去响应”。由于同步任务在后台 goroutine 中执行，点击同步本身可能立即返回，但随后整个管理端 API（列表、状态轮询、其他读写请求）都会卡住，直到大数据量同步结束。
- **根因：**
  1. **唯一数据库连接被长事务独占。** `store.Open` 设置 `db.SetMaxOpenConns(1)`，所有 API 和后台任务共用同一条 SQLite 连接。`runSyncTask` 在 `TxImmediate` 中一次性写入数万/数十万条目、构建 keep 临时表并执行差量删除；该长事务持续期间，任何其他数据库操作都只能排队等待，表现为全站无响应。
  2. **逐条写库放大耗时。** `runSyncTask` 对每个 URL 条目先执行一次 `nextURLOrderTx` 再 `INSERT OR IGNORE`，大数据量下产生大量单行查询 + 单行写入；差量删除阶段又逐条插入临时表。该过程在大事务中进一步拉长锁持有时间。
  3. **缺少任务级超时/取消与进度回写。** 后台任务使用 `context.Background()`，HTTP 拉取虽有 60s 超时，但数据库写入阶段没有整体超时或取消手段；任务状态直到全部完成后才从 `running` 变为终态，期间用户无法获得中间反馈。
- **影响范围：**
  - 管理端所有依赖数据库的接口（素材池、订阅、用户、装配、设置等）在大同步期间不可用，表现为系统失去响应。
  - 大 URL 素材池同步无法可靠完成，甚至可能长时间卡在 `running`，影响后续同步/编辑/删除。
  - 若定时同步触发大列表，也会在无人操作时阻塞系统。
- **修复方向（候选，待深入研究后与用户确认）：**
  1. **拆分长事务为分批提交：** 将条目写入/删除拆成若干小事务（如每 1000 条提交一次），避免单次持锁过久；需要重新设计“全部成功才差量删除”的原子性与失败回滚语义。
  2. **后台同步使用独立数据库连接：** 为同步任务单独打开连接，配合 WAL 让 API 读不被写事务阻塞；但仍需处理写锁等待与 `busy_timeout`。
  3. **消除逐条排序查询：** 在内存中一次性计算 URL 段起始 `sort_order`，批量插入（multi-row `INSERT OR IGNORE`）或复用 prepared statement；临时 keep 表也改为批量写入。
  4. **增加条目数/耗时保护与进度反馈：** 对大列表设置合理上限或先提示风险；任务进行中定期更新 `per_url_json`/进度，或支持取消。
- **状态：** ✅ 已修复（2026-08-21，素材池同步改为批量写入并使用独立后台数据库连接；后端测试通过）

### R19-02 装配页一级 Tab 层级混乱：四个子平台与素材池平级展示

- **根因：** 装配页信息架构按平台平铺，未按“素材管理 / 构建动作”两个业务阶段分组。
- **影响范围：** 一级导航选项过多，用户难以区分“维护素材池”和“构建订阅/规则”；与用户期望的交互结构不符。
- **修复方向：** 将页面改为两个一级 Tab（或分段器）：`规则素材池` 与 `构建订阅/规则`；在“构建订阅/规则”内部再用二级 Tab/分段器选择四个子平台，并保持现有 `?tab=` 路由参数兼容或迁移。
- **状态：** ✅ 已修复（2026-08-21，装配页重构为“规则素材池 / 代理组 / 构建订阅·规则”一级 Tab，四个子平台整合到构建 Tab；前端构建/测试通过）

### R19-03 素材池详情使用页面内替换式分层，交互混乱

- **现象：** `frontend/src/views/admin/assembly/PoolTab.vue` 中点击素材池名称后通过 `detailID` 把当前列表区整体切换为 `PoolDetail` 内联视图（`v-if="detailID"`），而不是在弹窗/抽屉中打开详情。

- **影响范围：** 素材池管理操作路径混乱，尤其在多素材池场景下难以快速对比/返回。
- **修复方向：** 将 `PoolDetail` 改为 Modal/Drawer 弹层，列表页保持稳定；详情内仍保留条目分页、手动 CRUD、同步历史等能力。
- **状态：** ✅ 已修复（2026-08-21，素材池详情改为 Modal 居中弹窗）

### R19-04 构建/创建素材前缺少必选配置预检，用户大量输入后才被拒绝

- **现象：** 进入构建订阅/规则或创建素材相关流程时，前端没有在早期统一预检“至少已配置一个可用节点”“已配置目标平台/订阅”“已配置规则实体（sr-conf）”等前置条件；`PoolTab.save()` 创建素材池时也只校验名称与 URL 格式，不校验节点/平台等构建所需配置。后端 `internal/assembly/validate.go` 会在生成/预览时拒绝，但此时用户往往已经完成大量输入。
- **根因：** 前端缺少“开始构建前”的前置条件检查；装配上下文虽返回 `nodes/platforms/rules`，但页面只在具体步骤给出局部提示，未在入口做阻塞式预检。
- **影响范围：** 用户可能在填写完目标、头部、节点、规则后才收到“请先创建订阅条目/至少一个可转换节点”等错误，体验差。
- **修复方向：** 在“构建订阅/规则”入口（或创建素材池前按需）根据 `getAssemblyContext()` 做必选配置预检，缺少时给出明确引导（前往节点/平台/规则管理），并阻止进入后续流程；后端仍保留兜底校验。
- **状态：** ✅ 已修复（2026-08-21，构建 Tab 增加前置配置预检并阻止进入装配器）

### R19-05 装配生成/激活后系统无响应，所有 API 约 15s 后 `context canceled`

- **现象：** 拼装结束后点击“去激活版本”或随后操作时，系统卡死、无响应，前端重复报“网络连接错误”。容器日志显示多个请求在约 15s 后失败：
  ```text
  vpn-sub-1  | time=2026-08-21T14:43:55.442Z level=ERROR msg=内部错误 path=/api/admin/subscriptions msg="检查表 assembly_blueprints 失败: context canceled"
  vpn-sub-1  | time=2026-08-21T14:43:55.442Z level=WARN msg=读取布尔配置失败，使用默认值 key=debug_mode err="读取配置 debug_mode 失败: context canceled"
  vpn-sub-1  | time=2026-08-21T14:43:55.442Z level=INFO msg=http_request method=GET path=/api/admin/subscriptions status=500 latency_ms=15003
  vpn-sub-1  | time=2026-08-21T14:43:55.442Z level=ERROR msg=内部错误 path=/api/admin/platforms msg="context canceled"
  vpn-sub-1  | time=2026-08-21T14:43:55.442Z level=INFO msg=http_request method=GET path=/api/admin/platforms status=500 latency_ms=15004
  ```
  **补充（用户确认）：** 重启后进一步观察到平台数据疑似丢失：新建订阅时平台选择从三个平台变为“0”（平台列表为空的表现）。该现象属于 R19-05 同一异常事件后的补充，需一并排查数据库持久化/数据卷状态，不作为独立问题。
- **根因：**
  1. 日志中的 `context canceled` 不是数据库损坏，而是请求等待数据库连接超过前端 Axios 15s 超时后，客户端取消请求导致后端 context 被取消。
  2. 根本原因仍是 `store.Open` 的 `db.SetMaxOpenConns(1)`：一旦某个后台/装配/同步相关操作长时间持有唯一 SQLite 连接或长事务，后续所有 DB 查询只能排队，超过 15s 即表现为全站网络错误。
  3. 装配生成/激活可能触发异步候选集重算（`RecomputeCandidateSet`）或之前的大素材池同步仍在运行，具体占用连接的任务需要结合 `pool_sync_tasks` 状态、goroutine/日志进一步确认。
- **影响范围：** 全站管理端不可用，任何依赖数据库的接口都会超时；用户看到“网络连接错误”，但数据本身未必损坏。
- **修复方向：**
  1. 与 R19-01 合并治理：拆分长事务、后台任务使用独立连接或分批提交，避免单连接被长时间独占。
  2. 为所有后台 DB 任务增加可观测性与超时/取消；前端路由守卫 `/api/system/status` 的请求也应加超时，避免无限等待。
  3. 紧急恢复手段：重启容器通常可释放被占用的连接；若存在残留 `running` 任务，服务启动逻辑会将其标记为 failed（见 `cmd/server/main.go`）。
- **状态：** ✅ 已修复（2026-08-21，数据库无响应问题已通过独立后台连接 + 批量写入缓解；重启后平台数据丢失补充现象仍需现场数据库/WAL/数据卷排查）

### R19-06 节点新建/编辑表单布局过宽，输入控件未限制合理尺寸

- **现象：** `frontend/src/views/admin/NodesView.vue` 新建/编辑节点使用宽度 720 的 Modal，但动态协议字段区每个字段都直接渲染为全宽 `Input` / `InputNumber` / `Select` / `TextArea`，没有按字段类型和常用组合做栅格/宽度限制。宽屏下输入框几乎占满弹窗宽度，用户反馈“占据整个屏幕”。
- **根因：** 动态表单渲染逻辑仅按 schema 顺序输出 `mb-3` 整行控件，未对协议字段做分组和列宽规划。
- **影响范围：** 新建/编辑节点表单可用性差，字段较多时视觉拥挤、难以浏览；与用户期望的紧凑表单不一致。
- **修复方向：** 重构节点表单布局：基础字段已使用 grid，协议动态字段也按字段类型/关联关系放入 2~3 列栅格；长文本或特殊字段单独限宽；`TextArea`（如 OpenVPN client-config、JSON 兼容字段）限制最大宽度与行数。
- **状态：** ✅ 已修复（2026-08-21，节点动态表单改为 2 列栅格布局）

### R19-07 REALITY 公钥/私钥/ShortId 应拆分为独立字段，而非单个 JSON

- **现象：** `backend/internal/node/registry.go` 中 VLESS 的 REALITY 配置被定义为单个 object 字段 `reality-opts`，前端动态表单因此渲染为一个 JSON `TextArea`，用户需要手写类似 `{"public-key":"...","short-id":"..."}` 的 JSON；且当前没有 `private-key` 的独立输入。用户期望 REALITY 公钥、私钥等拆分为两个（或多个）独立值。
- **根因：** 协议注册表把 REALITY 参数整体建模为 object，前端对 object 类型只能提供 JSON 编辑，未提供结构化字段。
- **影响范围：** 手工编辑 JSON 易出错，公钥/私钥语义不清晰；私钥若存在也缺少独立、可加密存储的字段表达。
- **修复方向：** 将 VLESS `FormSchema` 中的 `reality-opts` 拆分为独立字段，例如 `public-key`、`private-key`、`short-id`；私钥使用 `password` 类型并加入 `SensitiveFields`；后端校验、`assembly/links.go` 的 `realityOpts` 渲染读取兼容新字段，同时保留对旧 `reality-opts` 数据的兼容解析。
- **状态：** ✅ 已修复（2026-08-21，VLESS schema 拆分为 public-key/private-key/short-id，渲染兼容新字段与旧 reality-opts）

### R19-08 代理组管理应整合到“订阅装配”内作为 Tab，而非独立大版块

- **现象：** 当前代理组管理是独立路由 `/admin/proxy-groups`，并在管理后台侧边栏作为独立菜单项“代理组”展示；用户期望将其作为“订阅装配”内的一个 Tab（或与规则素材池、构建订阅/规则并列的装配子页），而不是独立大版块。
- **根因：** 导航与页面结构把代理组当作独立业务模块，未与装配流程的“节点/代理组/规则素材”统一组织。
- **影响范围：** 管理后台一级菜单过多，代理组与装配流程割裂，用户需要在装配页和代理组页之间来回跳转。
- **修复方向：** 将代理组管理页整合进 `AssemblyView`（或“订阅装配”大 Tab 下的二级 Tab），例如在装配页中增加“代理组”Tab；同步移除侧边栏独立入口 `/admin/proxy-groups`（或改为跳转到装配页对应 Tab），并保持现有路由兼容。
- **状态：** ✅ 已修复（2026-08-21，代理组作为“订阅装配”一级 Tab，移除独立路由与侧边栏入口）

### R19-09 代理组“节点引用排序”应在订阅装配中对已勾选组进行，而非单独在代理组设置中

- **现象：** 当前“节点引用（有序）”排序能力只在独立代理组管理的编辑弹窗中提供（上移/下移/拖拽）。在订阅装配的“节点与代理组”步骤中，用户勾选代理组后没有针对该组的节点引用排序交互；preset 组也没有排序入口。用户期望在装配时，根据上方已勾选的节点，对勾选上的代理组直接调整节点顺序，而不是先去代理组设置里单独排序。
- **根因：** 装配数据模型 `GenerateInput` 目前只有 `group_names`（勾选了哪些组），没有保存“每个勾选代理组在本次装配中的节点引用顺序”；渲染时仍直接使用代理组全局定义里的 `nodes` 顺序。
- **影响范围：** 同一代理组在不同订阅/规则装配中无法按本次勾选节点灵活排序；用户需要跨页面往返操作，装配体验割裂。
- **修复方向：** 在装配“节点与代理组”步骤中，为已勾选的代理组提供基于上方已勾选节点的引用排序 UI（上移/下移/拖拽，并只能引用已勾选节点）；扩展 `GenerateInput` 与蓝图 `selection_json` 保存每组覆盖顺序（如 `group_node_orders: { groupName: string[] }`）；渲染时若存在本次覆盖则优先使用，否则回退到代理组全局定义。
- **状态：** ✅ 已修复（2026-08-21，装配输入/蓝图新增 `group_node_orders`，渲染优先使用本次覆盖顺序；UI 提供上移/下移/移除）

### R19-10 节点表单 REALITY 等输入应在失焦/完成后校验，而非每输入一个字符即时报错

- **现象：** 新建节点面板中 REALITY 当前使用 object/JSON `TextArea`，`NodesView.vue` 的 object 分支在 `@change` 中每次输入都尝试 `JSON.parse`；输入尚未完成时反复弹出“对象字段 JSON 格式错误”。用户期望输入完成、焦点移出后再校验。
- **根因：** 动态表单的 object 分支把“解析”和“校验/错误提示”绑在 change 事件上，使用 `Notify.error` 全局提示，导致每敲一个字符都可能报错。R19-07 拆分 REALITY 后如果仍沿用 `@change` 校验，问题会跟随到新字段。
- **影响范围：** 新建/编辑节点时 REALITY 输入体验差；其他文本/密码/TextArea 字段当前虽无即时校验，但后续若在 `@change` 中加入校验也可能出现同样问题。
- **修复方向：**
  1. 对 REALITY 拆分后的独立字段使用 `@blur` 或保存时统一校验，不在 `@change` 中即时报错。
  2. 对象类型字段若仍需 JSON 编辑，也应改为失焦时解析/校验，错误用字段级提示而非全局 Notify。
  3. 排查节点表单及其他动态表单是否存在同类“change 即校验”的输入框，统一改为 blur/提交校验。
- **状态：** ✅ 已修复（2026-08-21，节点表单 object 字段改为 blur 解析 + 字段级错误提示）

### R19-11 OIDC 模拟登录邮箱字段名与 v-model 不一致，导致邮箱永远校验失败

- **现象：** 初始化系统时选择 OIDC 模拟（Mock）后，登录页的 Dev 模拟登录邮箱输入栏始终报错，无法提交通过。
- **根因：** `frontend/src/views/LoginView.vue` 中模拟登录表单的 `Form.Item` 使用 `name="mock_email"`，但输入框实际绑定的是 `v-model:value="mockForm.email"`。表单校验会去读取 `mockForm.mock_email`，该字段始终为 `undefined`，因此 `required`/`type: 'email'` 校验永远失败，即使用户输入了合法邮箱。
- **影响范围：** Mock OIDC 登录不可用，初始化/调试 OIDC 流程被阻断。
- **修复方向：** 统一表单字段名：将 `Form.Item` 的 `name` 改为 `email`，或将 `v-model` 改为 `mockForm.mock_email`；同时建议邮箱规则增加 `trigger: 'blur'`，避免输入过程中过早提示。
- **状态：** ✅ 已修复（2026-08-21，`Form.Item name` 改为 `email` 并加 `trigger: 'blur'`）

### R19-12 订阅装配头部表单应按平台类型区分，并使用结构化表单而非统一 JSON

- **现象：** 当前订阅装配的“头部表单”步骤对 `clash-yaml`、`sr-subs`、`sr-conf` 都使用同一个 JSON `TextArea`（`HeaderStep.vue`），仅默认值不同；`generic-subs` 则提示无需填写。用户反馈这不符合各平台实际头部结构：
  - `sr-subs` 的头部应为 `REMARKS` 和 `STATUS`（参考 `docs/DocTemplates/Shadowrocket.subs.template.md`）；
  - `sr-conf` 应为 Shadowrocket Conf 自己的头部（参考 `docs/DocTemplates/Shadowrocket.conf.template.md`），而不是 Clash 形式；
  - 且各平台头部应像“新建节点”那样使用结构化表单字段，而不是让用户手填 JSON。
- **根因：** `HeaderStep.vue` 只按 `targetSyntax` 区分“是否显示”，未按平台类型渲染不同字段；装配输入 `fixed_params` 也以通用 JSON 承载，缺少各平台的结构化表单定义。
- **影响范围：** 用户需要手动编写 JSON 才能生成正确头部，容易出错；sr-subs/sr-conf 的实际输出与参考模板不一致。
- **修复方向：**
  1. 为每个平台类型定义独立的头部字段 schema（Clash / SR subs / SR conf / Generic subs），前端按 `targetSyntax` 渲染结构化表单（Input/InputNumber/Switch 等），类似节点动态表单。
  2. `sr-subs` 至少提供 `REMARKS`、`STATUS` 字段；`sr-conf` 按 `Shadowrocket.conf.template.md` 提供 General 等头部字段。
  3. 后端 `fixed_params`/蓝图继续存储结构化值，渲染时按平台输出对应头部。
- **状态：** ✅ 已修复（2026-08-21，HeaderStep 按平台渲染结构化字段并提供“高级 JSON”切换；后端渲染原有 sr-subs/sr-conf 头部输出保持不变）

   - 如增加取消/上限，前端需有对应提示。

## 二、格式说明（新问题记录模板）

发现问题时，按以下结构追加到「进行中问题」：

```
### RXX-01 问题标题

- **现象：** ...
- **根因：** ...
- **影响范围：** ...
- **修复方案：** ...（决策后同步更新至 BuildN 对应 Step）
- **状态：** ☐ 待修复 / ◧ 修复中 / ✅ 已修复（日期 + 验收命令）
```

**流程约定：**

1. 问题发现 → 记录现象/根因/影响范围；
2. 存在方案取舍时，使用提问工具附推荐选项与用户确认；
3. 修复方案确定后，由 [BuildN.md](../BuildN.md) 承接为构建 Step；
4. 修复完成并验收通过后，更新状态为 ✅ 并记录验收命令与实际结果；
5. 非问题的优化候选 / 已知遗留事项归 [Design2.md](../Design/Design2.md) §三「后续设计候选」记录，不记录在本文件。
