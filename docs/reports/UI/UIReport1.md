# VPN 订阅管理系统 UI / UX 研究报告（UIReport1）

> **文档定位：** 本报告是一次仅针对前端视觉系统与用户体验的研究记录。依据为 [Design1-UI.md](../../reports/Design/Design1-UI.md)、[Design2-UI.md](../../../Design2-UI.md)、2026-08-28 的前端源码及本地浏览器走查结果。本文不改变产品功能、权限模型或后端契约，也不是已批准的 Design / Build 文档；候选项仍需用户确认后才能进入设计与构建。
>
> **结论先行：** 当前 UI 已具备完整路由、明暗主题和主要移动端分支，功能密度也适合小团队工具，但仍接近“Ant Design 默认组件拼装”的工程界面。第二轮按完整用户旅程核验后，优先级进一步明确：应先修复无效重置链接、OIDC 回调错误、手机管理顶栏、手机复杂表单和装配器技术枚举等会阻断或误导任务的问题；再建立完整视觉 Token、重组管理导航、拆分超长设置页、统一页面骨架与状态容器。导航分组与 Design2-UI 的既有平铺规格冲突，已列为待用户决策项，本文不擅自改写设计结论。

### 1.1 目标

- 让界面在不更换 Vue 3、Ant Design Vue 与 Tailwind 技术栈的前提下更美观、更易读、更容易完成任务。
- 覆盖所有现有前端路由，检查视觉层级、信息架构、响应式、交互反馈、中文文案与无障碍。
- 将事实、判断与假设分开，并给出可落地的组件方案、伪代码、实施顺序和验收方法。

### 1.2 范围边界

## 三、当前 UI 总体评价

### 3.1 视觉风格

当前界面干净、克制、没有无关装饰，但视觉辨识度较低。主色、圆角、阴影、字号和中性色大多沿用组件默认值，导致不同业务模块看起来像同一组表格与弹窗的排列。[浏览器][代码]

桌面截图中主要内容只占可视区域上部，文字尺寸偏小，空白不是经过设计的呼吸感，而是内容容器缺少最大宽度、最小高度和空状态节奏造成的“空”。暗色模式虽没有明显不可读区域，但页面背景、卡片和侧栏之间差异小，层级主要靠细边框，长时间使用容易疲劳。[浏览器]

### 3.2 信息架构

- 管理端基础模式已有 10 个平铺入口，高级模式再增加“用户组”和“Xray 实例”。“订阅、分享、平台、规则、订阅装配、节点”属于同一业务链，却在单层列表里和“用户、审批、日志、配置”混排。[浏览器][代码]
- “面板配置”包含身份认证、验证码、SMTP、站点、模式、限流、日志、内容、导入导出、备份与危险操作，远超单页可快速理解的范围。[浏览器]
- “订阅装配”内部同时有规则素材池、代理组和多类装配器，页面副标题直接描述实现步骤，适合作为内部开发注释，不适合作为面向用户的页面说明。[浏览器]

### 3.3 交互反馈与状态

Notify、ConfirmModal、loading 和 Empty 已覆盖大多数基础状态，属于可靠基线。问题在于状态表达的“质量”不统一：有的空状态有插图和动作，有的只有一行灰字；有的按钮表达任务（“新建订阅”），有的表达实现（“装配生成”）；有的禁用按钮附 Tooltip，有的没有下一步指引。[代码]

### 3.4 文案

管理员页面偏技术说明，用户页面相对友好。主要问题有四类：

1. 把内部概念当作用户已知，例如 `product_type` 对应的 `yaml / subs / generic-subs`。
2. 用“暂无”“失败”“未开启”描述状态，却没有告诉用户如何继续。
3. 危险提示堆叠技术后果，缺少“先说会发生什么，再说为何”的结构。
4. AntD 中文按钮出现“登 录、返 回、删 除”式字符间距，视觉上不自然。[浏览器]

### 3.5 无障碍

- 优点：页面有 heading、banner、main、menu 等语义结构，表单大多有 Form.Item label。[浏览器]
- 风险：主题 Switch 的可访问名称主要表现为 emoji；纯图标侧栏收起后依赖图形辨认；辅助文本常使用很浅的灰色和 12px；部分规则只放在 placeholder；颜色 Tag 可能成为唯一状态线索。[代码][浏览器]
- 键盘焦点、弹窗回焦、跳过导航和 `prefers-reduced-motion` 未形成全局规范。[代码]

## 四、建议的全局视觉系统

### 4.1 视觉方向

建议采用“清晰的运维工作台”方向：保留科技蓝和 Ant Design 的稳定感，但用更成熟的中性色、较大的排版、分层表面、任务型图标和一致的页面节奏建立产品辨识度。不建议改成高饱和渐变、大玻璃拟态或重动效，这些风格会降低长表格和配置页的可读性。

### 4.3 页面骨架

所有管理页建议统一为四层：全局导航 → PageHeader → 可选 ContextBar → Section/Card。页面背景不再额外套一个覆盖全高的大白卡，空状态放进有合理最小高度的 Section。

### 4.4 组件规范

| 组件 | 建议 |
|------|------|
| PageHeader | 标题 24px；副标题用用户目标描述；主操作仅一个；危险操作不得进入主操作位 |
| SectionCard | 12px 圆角、1px 边框、轻阴影；标题区与内容区间距固定 |
| DataTable | 表头更轻、行高至少 48px；主字段固定左侧；次要操作收进“更多”菜单 |
| MobileCard | 关键字段 3–4 项；底部一个主操作；次要/危险操作放菜单；触控目标至少 44px |
| FormSection | 每组不超过 6–8 个字段；组标题说明影响；帮助文本不只放 placeholder |
| EmptyState | 标题说明“现在是什么状态”，描述说明“为什么/如何继续”，最多两个动作 |
| StatusBadge | 图标/文字/颜色三者至少两种同时表达；状态词全局统一 |
| ConfirmModal | 第一段说明结果，第二段列影响；确认按钮使用具体动词，如“删除节点” |
| Toast | 成功只说明结果；失败说明原因与下一步；长任务用可持续 Notification |
| CopyField | 明确内容类型与敏感性；复制后提示“已复制订阅链接，请勿公开分享” |

## 五、导航与信息架构改进

### 5.1 管理导航分组

当前平铺菜单是 Design1 时期的明确决定，但 Design2 增加模块后已不再适配。建议下一轮设计允许分组，并保留收起态 Tooltip：

```text
概览
  返回主界面

分发管理
  订阅
  分享
  平台
  规则

装配资源
  订阅装配
  节点
  用户组（高级）
  Xray 实例（高级）

成员与权限
  用户
  审批中心

系统
  面板配置
  日志
```

推荐默认展开当前分组；其他分组保持可见但压缩。收起侧栏时每个图标必须有 Tooltip，组分隔仍以细线体现。手机 Drawer 在顶部显示当前页面和关闭按钮，底部固定“返回主界面”。

### 5.2 设置页重组

建议保持 `/admin/settings` 路由不变，在页内改成左侧锚点导航或 Tabs + 分组卡片：

- 身份与访问：OIDC、本地认证、验证码。
- 通知：SMTP。
- 外观与内容：站点名称、ICON、公告、页脚。
- 运行与安全：模式、限流、连接超时、日志、调试。
- 数据管理：导入导出、备份。
- 危险操作：始终独立红色区域，默认折叠。

每组提供独立保存条，保存后仅反馈该组。页面头显示“未保存更改”状态，切换分组或离开页面时提醒。

### 5.3 装配页重组

- 页面说明改为“组合节点、代理组和规则，生成可发布的订阅或分流规则”。
- 顶层导航以三个任务命名：“规则素材”“代理组”“生成配置”。
- “生成配置”内部再选择 Clash / Shadowrocket / 通用节点 / 分流规则，避免标题里出现“四类装配器”。
- 步骤条只显示当前任务需要的步骤；移动端用紧凑步骤标题和固定底部“上一步/下一步”。

## 六、全路由 UI / UX 审计矩阵

> “实机”表示浏览器直接到达或由正常流程到达；“静态”表示受状态/动态参数限制，依据组件源码核验。

### 6.1 公共与认证路由

| 路由 | 证据 | 主要问题 | 建议 | 优先级 |
|------|------|----------|------|--------|
| `/setup` | 实机 | 1440px 下卡片和文字偏小；导入区直接引用 `Design1 §3.4.8`；三张选择卡的可点击范围与选中状态不明显 | 提高容器至 760–800px、标题 24px；整卡可选；把内部文档引用改成人话 | P1 |
| `/login` | 实机 | 品牌区弱；主题开关游离在卡片右下；首管理员提示和登录任务竞争注意力 | 统一 AuthShell；主题按钮固定右上；管理员提示压缩为卡片内上下文提示 | P1 |
| `/register` | 实机 | 密码规则未在提交前说明；页面与登录页品牌结构不一致 | 字段下常驻密码要求与实时满足状态；复用 AuthShell | P0 |
| `/forgot` | 实机 | 只有标题和表单，缺少“会发生什么”的说明 | 增加“输入账号邮箱，我们会发送 1 小时有效的链接” | P1 |
| `/reset` | 实机（第二轮复核） | 无 token 时仍展示两个密码字段和“确认重置”，用户只能提交后才知道链接无效；密码规则只依赖校验 | 无有效链接时直接显示 Result；区分缺失、过期、已使用；补密码要求与显示/隐藏按钮名称 | P0 |
| `/pending` | 实机 | 状态明确，但没有刷新或下一步说明 | 增加“审批后重新登录即可”，可选“返回登录”与“刷新状态” | P2 |
| `/login/callback` | 实机（无 ticket 失败分支） | 中转页只有“正在登录…”；失败后返回登录页并直接展示内部值 `exchange_failed`，没有原因、重试或帮助 | 映射为用户可读错误；保留“重新使用 OIDC 登录 / 使用本地账号 / 联系管理员”恢复路径；关联错误编号而非暴露内部枚举 | P0 |
| `/emergency` | 静态 | 高风险页面字段密集；红色警示易掩盖操作步骤 | 使用编号步骤、固定风险摘要、清晰区分“重置密码”和“重新初始化” | P0 |
| `/:pathMatch` | 实机 | 404 文案可用但品牌和帮助弱 | 增加站点名、返回首页和返回上一页；不展示技术路径 | P2 |

### 6.2 用户路由

| 路由 | 证据 | 主要问题 | 建议 | 优先级 |

## 八、响应式专项建议

### 8.1 桌面（≥1200）

- 内容区设置 `max-width: 1440px` 并居中；表单型页面建议 `max-width: 960px`，避免字段无限拉宽。
- 页面标题 24px，主内容正文至少 14px/22px；不要以大量 12px 灰字承担核心说明。
- 空状态 Section 的建议高度为 280–360px，不让空插图漂浮在整屏大容器中。
- 三列卡片仅用于信息对等的平台；设置和装配继续使用单列任务流。

### 8.2 平板（768–1199）

- 不能简单沿用桌面表格。操作列超过两个按钮时统一折叠；非关键列允许隐藏或进入展开行。
- 侧栏建议默认收起，但保留 Tooltip；内容内边距从 24 降为 20。
- 设置页使用顶部下拉分组代替左侧锚点，避免双侧栏挤压。
- 本次平板截图采集失败，以上关于视觉比例的结论属于**源码与断点推断**，实施前需补实机截图复核。

### 8.3 手机（<768）

- 手机双态列表方向正确，应扩展到所有列表，不允许局部回退为可横向滚动的大表格。
- 顶栏保留菜单、站点名、用户菜单三个核心元素；管理入口和主题切换进入用户菜单或设置抽屉。
- 页面头动作超过两个时只保留主操作，其余进入“更多”。
- 表单弹窗在手机改为全屏 Drawer；底部固定提交区并尊重安全区 `env(safe-area-inset-bottom)`。
- 触控目标至少 44×44px；当前大量 `size="small"` 按钮只适合桌面表格，不适合作为手机主操作。
- 装配步骤和长设置页需提供页内进度/目录，避免用户失去位置。
- 390px 实测管理顶栏同时放置汉堡、站点名、用户名与主题开关时，用户名被压缩成近似单字符按钮、主题开关贴近右侧边界；应只保留汉堡 + 站点名 + 一个“账户”入口，主题切换收入账户菜单。
- 复杂编辑不得继续使用固定宽度居中 Modal。390px 的“新建节点”首屏只显示约半组字段，底部确认区完全不可见；建议改为全屏 Drawer，顶部固定标题/关闭，底部固定“取消/保存”，字段按“必填连接信息/协议扩展/传输与 TLS/高级网络”渐进展开。

## 九、无障碍专项建议

1. 所有图标按钮提供稳定的 `aria-label`；收起侧栏同时提供 Tooltip 与可访问名称。
2. 主题控件使用“切换到深色模式/切换到浅色模式”，emoji 仅作装饰并 `aria-hidden`。
3. 页面只保留一个 `h1`；Section 使用 `h2`，卡片标题使用 `h3`，避免管理页从 `h2` 开始。
4. 所有 Form.Item 帮助文本与输入框通过 `aria-describedby` 关联；规则不能只放在 placeholder。
5. 成功/警告/失败除颜色外同时使用图标和文字；Tag 文本必须独立可理解。
6. 键盘焦点使用 2px 高对比 focus ring，不用浏览器默认样式被 Tailwind/AntD 清除。
7. Modal 打开后焦点进入标题或首字段，关闭后回到触发按钮；危险确认词输入需有明确说明。
8. Toast 对关键失败使用 `role="alert"`，普通成功使用非打断式 live region。
9. 全局支持 `prefers-reduced-motion`，关闭进度条和 Drawer 的非必要过渡。
10. 浅色次要文字和暗色边框需通过 WCAG AA 对比度检查；正文目标至少 4.5:1。

- **目标：** 让核心任务无需理解内部实现，并满足基础键盘/读屏要求。
- **影响范围：** 页面可见字符串、表单帮助、按钮名称、状态 Badge。
- **伪代码：**

```ts
const productTypeLabels = {
  yaml: 'Clash YAML',
  subs: 'Shadowrocket 节点订阅',
  'generic-subs': '通用节点订阅',
}

const statusLabels = {
  pending: { label: '等待处理', icon: ClockIcon },
  running: { label: '处理中', icon: LoadingIcon },
  succeeded: { label: '已完成', icon: CheckIcon },
  failed: { label: '失败', icon: ErrorIcon },

```

- **验收：** 内部枚举不直接展示；按钮具有唯一可访问名称；Tab 键顺序符合视觉顺序；颜色不是唯一状态信号。

## 十三、第二轮完整用户旅程核验

### 13.1 核验口径

第二轮不再只按路由逐页看视觉，而是按“用户从哪里来、想完成什么、遇到问题如何恢复、完成后去哪里”检查连续流程。浏览器只执行读取、导航、切换页签、打开并取消表单等无数据副作用操作；创建、保存、发送、导入、删除和外部认证不执行。因此下表将“入口与空态实机可达”和“有数据后的业务闭环静态核验”明确分开。

证据等级：

- **A：浏览器连续操作核验**，包括入口、跳转、页面状态和恢复路径。
- **B：浏览器到达页面 + 源码/设计补齐**，未提交会改变数据的动作。
- **C：源码/设计核验**，受高级模式、外部系统或动态 ID 限制。

### 13.2 旅程覆盖矩阵

| 旅程 | 预期路径 | 证据 | 核验结果 | 主要缺口 |
|------|----------|------|----------|----------|
| 首次部署 | Setup → 创建首管理员 → 登录 → 首页 | B | Setup、注册、登录页面结构完整 | Setup 仍暴露内部 Design 编号；认证页缺统一 AuthShell；未实际新建账号 |
| 本地登录 | 登录 → 首页 → 个人中心 → 返回首页 | A/B | 首页与个人中心可达，基础信息/密码页签存在 | 个人中心脱离通用 Header；按钮均叫“修改”，缺对象；本轮未提交登录凭据 |
| 忘记密码 | 登录 → 找回 → 邮件链接 → 重置 → 登录 | A/B | 找回与重置入口可达 | 无 token 仍可填写并提交；缺少“邮件有效期/查收位置/未收到怎么办”；未发送邮件 |
| OIDC 登录失败 | OIDC 回调 → 失败 → 登录恢复 | A | 无 ticket 时实际回到 `/login` | 直接展示 `exchange_failed`；没有重试、替代登录或联系管理员路径 |

### 13.3 首次发布旅程的核心问题

当前系统把“平台、订阅条目、节点、装配蓝图、版本、激活”分别放在不同页面，但没有一处用用户任务解释它们之间的依赖。新管理员会从任一空态开始试错，而不是沿着可见的完成路径前进。浏览器实测装配器能提示“至少一个可用节点”和“目标平台未创建订阅池”，也能跳到对应页面，这是一条好基础；问题是跳转后用户只看到普通列表页，完成动作后没有“返回装配并继续”的上下文。

建议把首次发布做成**非强制任务清单**，不是新增阻塞式向导：

```text
发布第一份订阅
1. 已有平台                         已完成
2. 创建订阅条目                     待完成 → 新建订阅
3. 添加至少一个节点                 待完成 → 添加节点
4. 生成并预览配置                   未开始
5. 激活版本                         未开始
6. 以普通用户视角检查               未开始
```

- 只在尚未完成首次发布时出现在管理首页/订阅空态顶部；完成后自动折叠为“发布流程帮助”。
- 每一步都使用现有 API 状态判断，不新增统计服务；本文只提出信息架构，不决定实现细节。
- 跨页入口附带 `return_to` 或由前端保存“当前任务”上下文，完成节点/订阅创建后提供“返回装配”主动作。
- 不把业务对象合并成一个大向导，避免高级用户被锁入线性流程。

### 13.4 管理员日常任务模型

首次发布之后，管理员更关心异常和待办，而不是对象总数。建议未来管理入口优先展示现有状态可推导的四类任务：

1. 未激活版本：已经生成但用户仍看不到。
2. 失败任务：素材同步、装配、Xray 同步或对账失败。
3. 待审批用户：需要人工处理。
4. 配置风险：SMTP/OIDC/高级模式等已启用但缺少必要配置。

如果暂不新增管理概览路由，可先在对应菜单项和页面头使用 Badge/Alert 表达，不必新增后端指标。所有提醒都应提供“处理”与“稍后”路径，不能只显示警告。

## 十五、目标体验蓝图

### 15.1 全局壳层

```text
AppShell
├─ PrimaryNav：按任务域组织模块
├─ AppHeader：站点 / 当前上下文 / 账户
└─ PageShell
   ├─ Breadcrumb（仅层级或跨对象页面）
   ├─ PageHeader（唯一 h1 + 描述 + 1 个主操作）
   ├─ ContextBar（来源任务、未保存、前置条件、后台任务）
   └─ StateContainer
      ├─ Loading
      ├─ Error + Retry
      ├─ Empty + Next action
      └─ Content sections
```

ContextBar 是第二轮最重要的新增建议：它解决“从装配跳去补节点”“从版本回到订阅”“从用户进入自定义订阅”等跨页任务丢失问题，但不改变路由和 API。

### 15.2 复杂表单的渐进披露

复杂表单统一分三级：

- **必须现在决定：** 名称、目标、协议、服务器、端口等任务必填项。
- **通常需要：** TLS、传输、认证和常用策略。
- **高级选项：** JSON 参数、出站网卡、路由标记、MPTCP 等；默认折叠并显示已配置数量。

保存失败时在顶部给出错误摘要，同时把焦点移到第一个错误字段；折叠区内有错误时自动展开。手机使用全屏 Drawer，桌面可用宽 Modal 或独立页面，但同一业务只维护一套字段分组。

### 15.3 错误与恢复规范

错误信息统一成四段，其中后两段按需出现：

1. **发生了什么：** “无法完成 OIDC 登录”。
2. **当前结果：** “你的账号和现有登录状态没有改变”。
3. **可能原因：** “登录请求已过期，或身份提供商暂时不可用”。
4. **下一步：** “重新登录 / 使用本地账号 / 联系管理员并提供错误编号”。

内部错误 key、HTTP 状态、任务 ID 不直接作为主文案；可以折叠进“技术详情”供管理员排查。表单校验错误在字段旁显示，跨字段/后台错误用 Alert，短暂成功用 Toast，长任务用可持续 Notification 或页面内状态条。

### 15.4 普通用户首页

普通用户首页应回答三件事：当前能否使用、用哪个客户端、下一步是什么。建议顺序：

1. 账户/服务状态摘要（正常、待发布、已停用等）。
2. 推荐平台卡片（按管理员配置顺序，不新增推荐算法）。
3. 分流规则（仅对 Shadowrocket 用户清楚说明先后顺序）。
4. 流量信息（高级模式或启用时显示）。

管理员访问用户首页时加“管理员预览”ContextBar，并提供“返回管理后台”，避免把无可用版本的管理员预览误认为普通用户真实状态。

- 设置项可在 10 秒内通过分组导航找到；未保存区清楚。
- 1440/1024/390 三档核心页面完成浅色与暗色快照。
- axe 自动检查无 critical，主要旅程无 serious；人工键盘检查通过。

### Phase C：全旅程迁移

范围：首次发布任务清单、版本管理上下文、用户/审批/日志、平台与分享文案、复杂有数据状态。

## 十七、待用户确认的设计决策

以下内容存在多种合理方案或与当前设计文档冲突。本文只给推荐，不把它们写成已批准结论。

### D1：管理导航是否从平铺改为分组

- **方案 A（推荐）：分组但不折叠。** 以“分发管理 / 装配资源 / 成员与权限 / 系统”显示分组标题，所有入口仍一眼可见。优点是扫描成本低、不会多一次点击；代价是与 `Design2-UI.md §2.1`“平铺不分组”冲突，需要用户批准后同步 Design。
- 方案 B：可折叠分组。更节省高度，但会隐藏入口并增加状态管理，不适合只有 10–12 项的小系统。
- 方案 C：保持平铺，只调整顺序和分隔线。改动最小，但无法建立清晰任务域。

### D2：设置页的分区承载方式

- **方案 A（推荐）：同一路由 + 左侧分组导航；手机改 Select。** 保留 `/admin/settings` 和现有 API，支持 `#identity` 等深链；改动集中、迁移风险低。
- 方案 B：每组独立子路由。浏览器前进/后退和权限更清晰，但路由、加载与未保存管理更复杂。
- 方案 C：顶部 Tabs。实现简单，但 6 个分组在手机拥挤，且跨 Tab 的未保存状态不直观。

### D3：手机复杂表单载体

- **方案 A（推荐）：手机全屏 Drawer，桌面宽 Modal/页面。** 与现有组件栈一致，能固定底部操作；需要共享同一表单组件避免双份逻辑。
- 方案 B：全部改独立页面。深链和恢复最好，但会扩大路由与面包屑范围。
- 方案 C：保留 Modal 只增加内部滚动。改动最小，仍难表达分组和进度。

### D4：首次发布任务清单放置位置

- **方案 A（推荐）：订阅页空态顶部 + 完成后折叠。** 不新增管理概览路由，符合轻量化原则。
- 方案 B：新增 `/admin` 概览。长期扩展性好，但需要明确指标和新页面定位。
- 方案 C：只改善各页空态。改动最小，但跨页依赖仍不可见。

## 十八、最终建议

不要从单页“美化”开始。第二轮实测表明，第一步应修任务阻断：无效重置、OIDC 错误、手机 Header、复杂表单、装配类型名称和跨页返回。第二步确认 D1～D4，再落地视觉 Token、PageShell / StateContainer / FormSection 与设置/装配信息架构。第三步使用一份可重建的测试数据完成带数据的端到端旅程，最后才批量润色图标、插图和动效。

建议下一步由用户先确认 D1～D4 和首轮是否只覆盖 Phase A。确认后再把结论同步到 Design 文档，并按 `Build.template.md` 生成单独的 UI 构建计划；在用户明确下达构建指令之前，本报告保持为研究依据，不直接充当构建指令。
